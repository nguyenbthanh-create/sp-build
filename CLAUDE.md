# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A WordPress plugin ("SportPress Calendar PRO", internal name SP_Build, text domain `sp-cal-pro`, main file `sportpress-calendar-pro.php`) that runs the full logistics of a sports association: membership/adhesion, attendance (incl. QR pointage), calendar/planning, belt-grade exams and jury, competitions/palmarès, event inscriptions, notifications, a member-facing PWA, and a read-only public REST API. Code and comments point to a taekwondo club (`tkdclaira.fr` is hardcoded in `includes/class-updater.php`).

There is no build tooling, no package manager, no test suite, and no local WordPress/PHP runtime in this environment (no `php` binary available). This is pure PHP/JS/CSS meant to be deployed as-is into `wp-content/plugins/`. Verify changes by careful manual review against the conventions below and by deploying to the project's OVH test site — there is no way to lint, run, or execute this code in this sandbox.

- **Git is a local safety net, not for collaboration.** This folder had no version control before 2026-08-31 — it's a local-only repo (no remote) whose sole purpose is letting changes be reverted if something breaks on the test site. ## Architecture

### Bootstrap and dependency wiring

`sportpress-calendar-pro.php` requires every file under `includes/` and instantiates a single `SpCalPro` singleton, which builds one `SpCalPro_DB` instance (`$db`) and passes it into every feature class's constructor (`new SpCalPro_Admin($db, $token)`, `new SpCalPro_Calendar($db)`, etc.). `$db` is the shared data-access layer for almost the entire plugin.

Two coexisting patterns for wiring in new code, depending on age:
- **Older classes** (calendar, planning, notifications, pdf, jury, members, exam, inscriptions...) take `$db` (and sometimes `$token`) via constructor injection, instantiated once from `SpCalPro`'s or `SpCalPro_Admin`'s constructor.
- **Newer classes** (`SP_Front_Adhesion`, `SP_Admin_Adhesions`, `SP_Cal_Renouvellement`) are singletons via `get_instance()`, self-register their own hooks in the constructor, and are `require_once` + instantiated from inside `includes/class-admin.php` rather than the top-level plugin file. Follow this newer pattern for anything you add.

### The four surfaces

1. **wp-admin** (`includes/class-admin.php` + `class-admin-*.php`) — the menu, all settings, and most CRUD. `class-admin.php` (~4200 lines) is the biggest file: it registers the whole admin menu and delegates individual pages to submodules (`$this->members` → `class-admin-members.php`, `$this->exam` → `class-admin-exam.php`, `$this->jury` → `class-admin-jury.php`, `$this->inscriptions` → `class-admin-inscriptions.php`), but it *also* independently implements the entire mobile PWA (see below) and the global settings page in the same file.
2. **Public front-end shortcodes** — one class + one template per shortcode: `class-calendar.php`/`templates/calendar.php`, `class-eleves-front.php`, `class-palmares-front.php`, `class-bureau-front.php`, `class-top5-front.php`, `class-front-adhesion.php` (the `[sp_inscription_adhesion]` membership/renewal form, the most actively developed one right now).
3. **A member/trainer PWA** — entirely generated by one method, `SpCalPro_Admin::render_pwa_app()` (registered as the `[sp_cal_app]` shortcode), which `ob_start()`s and echoes ~1300 lines of inline HTML/CSS/JS as a single PHP string. It talks to a homemade JWT auth + REST API under the `spcal/v1` namespace (also defined in `class-admin.php`, plus overlapping/competing registrations in `class-ajax.php` — see `02-etat-des-lieux.md` for the known duplication).
4. **A public read-only REST API** — `includes/class-api.php`, namespace `sp-cal/v1`, key-authenticated, for external display use.

### Data layer

`includes/class-db.php` (`SpCalPro_DB`) owns almost the entire schema: table creation in `activate()` (on plugin activation) and incremental `ALTER`s in `maybe_upgrade()` (hooked to `admin_init`, runs on every admin page load), plus `table_*()` name-helper methods and most `get_*()`/`save_*()` query methods used across the plugin. Two tables are created *outside* this class as one-off exceptions: `sp_cal_push_subs` (in `class-admin.php`) and `sp_adhesions_pending` (in `class-front-adhesion.php`, via its own `SP_Front_Adhesion::create_table()` + a `sp_adh_schema_version` option guard hooked to `init` — this is the pattern to copy if you add a table outside `class-db.php`).

Table naming is *mostly* `{$wpdb->prefix}sp_cal_*` via `$db->table_*()` helpers, with known exceptions: `sp_adhesions_pending` (no `_cal_`) and `sp_jury_notes` (no `_cal_`). Don't assume a table name from convention — check `class-db.php` or the class that owns it.

The central member/student table is `sp_cal_eleves` — a wide, flat table (identity, adhesion, grade, family contacts, mensurations, a free-form `extra_data` JSON column used for anything that doesn't have a dedicated column). Pending public adhesion/renewal requests live separately in `sp_adhesions_pending` until an admin approves them (`class-admin-adhesions.php::create_member()` for new members, `update_member_renouvellement()` for renewals — the latter merges into the *existing* `extra_data` rather than overwriting it, to avoid losing unrelated history like CSV-imported grades).

### Known traps (see `02-etat-des-lieux.md` for the full audit)

- `class-jury-mobile.php` exists both at the plugin root and under `includes/` — only the `includes/` one is ever loaded; the root copy is dead and should not be edited.
- Several features (QR pointage, jury score calculation) have multiple independent implementations across files instead of one shared source of truth — check for siblings before assuming you found the only copy.
- Security rigor varies a lot by file; `class-admin-inscriptions.php` (consistent nonce + capability checks on every AJAX handler) is the style to imitate, not the average of the codebase.
- Prefer `SELECT *` over a named column list in any query on a table that gets columns added over time (e.g. `sp_adhesions_pending`) — a column not yet migrated on a given environment makes a named-column query fail entirely, silently emptying the whole result, whereas `SELECT *` degrades gracefully.
